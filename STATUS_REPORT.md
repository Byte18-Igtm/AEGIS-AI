## Phase 2 — Synthetic dataset (`data/generate_synthetic.py`)

**Working.** `python data/generate_synthetic.py` → `data/synthetic_telemetry.csv`
(+ `synthetic_telemetry_summary.json`). Deterministic (seed 42).

- 18 servers × 21 days × 5-min cadence = 108,864 rows.
- 700 incident windows: cpu_overload 161, error_burst 137, memory_pressure 134,
  traffic_spike 134, latency_degradation 134 — all well over the "100+ per type"
  target.
- Severity assigned from how far past threshold the injected magnitude sits.
  Window severity mix: low 249 / medium 200 / high 251.
- ~25% of windows are deliberately "borderline" (magnitudes straddling the
  low-severity threshold); incident onsets use raised-cosine ramps, and some
  incidents have realistic secondary effects (a traffic spike also raises CPU and
  latency). Result: classes are not linearly separable, which is the point.

**Grounding.** Only the normal-CPU baseline band, U(12, 42)%, is claimed to be
literature-grounded (Azure Public Dataset — Cortez et al., SOSP 2017). Memory,
latency, error-rate, traffic baselines and all incident magnitudes are plausible
but invented. This is stated in the script header and the README.

**Assumptions / shortcuts:**
- All five metrics come from one synthetic process per server; real fleets have
  correlations and failure modes this does not capture.
- Incident *durations* (30 min – 3 h) and *rate* (~40 per server per 21 days) are
  guesses, not calibrated to any incident database.
- `severity` thresholds are round numbers chosen by hand.

**Weak point a judge would hit:** "Your model is good because your data is
generated by rules, and your classifier is basically re-learning those rules."
Partly fair. Mitigations in place: whole-server held-out split, borderline
windows, ramped onsets, overlapping secondary effects, and the classifier still
shows a real precision gap on the confusable types (traffic_spike /
latency_degradation ≈ 0.80). It is not a perfect-score toy.

## Phase 3 — Anomaly detection + classification

**Working and validated. This is the part to lead with.**

- `src/features.py` — each 1-hour window (12 samples) → ~85 features: per-metric
  mean/std/min/max/last/range/delta/slope/max-rate-of-change, threshold-violation
  fractions, traffic ratio to a stored baseline, and cross-metric ratios /
  correlations (latency-per-rps, error-volume, cpu-mem correlation, latency slope
  minus traffic slope, …).
- `src/train.py`:
  - **Test split made before any fitting**, at the server level — servers
    `srv-14…srv-17` are held out entirely, so no training window shares a server
    with any test window.
  - IsolationForest (300 trees) fit on **normal windows only** → genuine novelty
    detector.
  - RandomForest for `incident_type` (400 trees, `class_weight="balanced"`,
    includes a `normal` class).
  - RandomForest for `severity` (300 trees), trained on incident windows only.
  - Saves `isolation_forest`, `rf_incident_type`, `rf_severity`, `metadata`
    (feature names, baseline traffic, normal-window stats, anomaly-score
    percentiles, split), and `test_set` (held-out X/meta) to `models/`.
- Wired into `pipeline.detect_anomaly` / `pipeline.classify_incident`, replacing
  the stubs. Both now operate on a **window** (consecutive samples for one
  server), not the whole frame.

**Held-out numbers** (`reports/evaluation_report.md`, 4,028 windows):
- incident_type: accuracy 0.97, macro-F1 0.92; per-class F1 0.87–0.98.
- severity: accuracy 0.88.
- anomaly detector: precision 0.71, recall 0.91, F1 0.80.

**Simplifications:**
- Windows are non-causal in the sense that a window straddling an incident onset
  is labelled by ≥40% row coverage; a few edge windows are genuinely ambiguous.
- The anomaly `anomaly_score` (0–1) is a linear map of the raw
  `-score_samples` value through the training-normal p50…p99 range, then clipped.
  It is a monotonic convenience score, not a calibrated probability.
- `anomalous_metrics` attribution is a simple "window mean > normal mean + 2·std"
  heuristic, independent of the IsolationForest internals.

**Weak points:**
- Anomaly precision 0.71 — it over-flags. Honest framing: "unlike normal" ≠ "is
  an incident", and on this data recall matters more.
- The classifier is strong partly *because* the generator is rule-based (see
  Phase 2 weak point).

## Phase 4 — Simulation + risk scoring

**Working and reproducible, but NOT validated against anything.** This is the
softest part of the project and should be presented as such.

- `src/actions.py` — `feasible_actions(incident_type)` → best-first action list
  from `ACTION_VOCAB`, always plus a `do_nothing` baseline.
  **Deviation from spec:** `do_nothing` is not in `ACTION_VOCAB`. It was added
  because Phase 6 explicitly wants "rank scale_out safer than doing nothing", and
  a no-op baseline makes the risk numbers interpretable. It is clearly marked as
  "not a real remediation" everywhere.
- `src/simulate.py` — Monte Carlo, 500–2000 draws (default 1000). Per draw it
  samples downtime (lognormal), post-action latency (uniform multiplier on the
  window's current latency), incremental cost (normal), and a latent recovery
  probability (Beta). Reports mean + p90 for each, plus raw draw arrays for
  charting.
- `src/risk.py` — each factor is blended (0.6·mean + 0.4·p90), min-max normalised
  **across the candidate set**, then combined with named weights
  (`downtime 0.30, latency 0.20, cost 0.15, recovery 0.35`, renormalised to 1).
  Lower score = safer. Includes `build_explanation()` which writes the
  recommendation text from the actual numbers (downtime, p90, recovery %,
  comparison to `do_nothing`, dominant differentiating factor vs. runner-up).
- Wired into `pipeline.simulate_action` / `pipeline.rank_actions`.

**The core honesty issue:** the per-action effect priors in `simulate.py`
(`_PRIORS`) are **hand-authored**. They encode reasonable domain intuition —
scale_out fixes cpu_overload and traffic_spike well but not a bad deploy;
rollback fixes error_burst; do_nothing downtime explodes with severity — but they
are **not fitted to data and there is no ground truth for action outcomes** in
the dataset. The simulation is a structured way to express assumptions, not a
measured predictor.

Consequences:
- The risk *ranking* is only as good as those priors.
- Because normalisation is within-candidate-set, `risk_score` values are relative
  to one incident and **not comparable across incidents**.
- p90 of `recovery_probability` is the p90 of the latent Beta draw, which is a
  slightly odd quantity; it is reported for interface completeness.

**Weak point a judge would hit:** "How do you know reroute_traffic actually beats
restart_service for latency_degradation?" Honest answer: we don't — the priors
say so. Validating this would need a real incident/response outcome dataset or a
proper infrastructure simulator, both out of scope.

## Phase 5 — Dashboard (`dashboard/app.py`)

**Working.** `streamlit run dashboard/app.py`.

- Scenario selector: curated windows from the **held-out** test set (a few per
  incident type across severities, plus normal windows).
- Shows detected incident + severity + confidences, anomaly score, ground-truth
  label (for demo verification), and which metrics are above normal.
- 5-panel telemetry chart of the selected window.
- Ranked action table (risk score, downtime mean/p90, latency, cost, recovery).
- Recommendation box with the **generated** explanation (not hardcoded).
- Per-action expander with histograms of the Monte Carlo downtime & latency
  draws.
- Sidebar sliders for the four risk weights and the draw count — the ranking
  updates live.
- `@st.cache_resource` loads models once; **the app never calls train**.

**Verification done:** launched headless (`--server.headless`), served HTTP 200
with a clean log; the full per-scenario pipeline was exercised via a script
(`predictions + rankings sane for all 5 incident types + normal`). **Not done:**
manual click-through of every widget in a real browser on this machine.

**Simplifications:**
- Scenarios are pre-selected windows, not an arbitrary time/server picker.
- Simulation is re-run on every widget change (seeded, so it's stable); for 4–5
  actions × 1000 draws this is fast enough but not optimised.

## Phase 6 — Evaluation + tests + docs

**Working.**

- `src/evaluate.py` → `reports/evaluation_report.md`,
  `reports/confusion_incident_type.png`, `reports/confusion_severity.png`.
  Contains `classification_report` for both classifiers and precision/recall/F1
  + confusion counts for the anomaly detector, all on the held-out servers.
- `tests/test_pipeline.py` — 5 pytest scenario tests, all passing:
  1. ranking is well-formed (ranks 1..n, ascending scores, recommendation =
     rank 1, weights sum to 1, non-trivial explanation).
  2. high-severity traffic_spike → `scale_out` risk < `do_nothing` risk, and the
     safest action is `scale_out` or `reroute_traffic`.
  3. high-severity error_burst → `rollback_deployment` risk < `do_nothing`, and
     `do_nothing` is not the safest.
  4. strong cpu_overload/high held-out windows → majority classify as
     `cpu_overload`.
  5. mean anomaly score over incident windows > mean over normal windows.
  Simulation draws are seeded, so 2 and 3 are deterministic.
- `README.md` rewritten: architecture, per-piece run commands, dataset
  description, evaluation numbers, and the synthetic-data honesty note.

**Flakiness:** tests 2 and 3 depend on the hand-authored simulation priors. They
pass comfortably now, but if `simulate.py::_PRIORS` is retuned they could break —
that's by design (they guard the priors' sanity). Tests 4 and 5 depend on the
trained models existing; the whole module `skip`s with a clear message if
`models/` is empty.

1. `BUILD_GUIDE.md` never existed → worked from the task message's phase spec.
2. Not a git repo → added `.gitignore`; did **not** run `git init` (left that to

   fine for a prototype.

   CSVs in `data/` via glob and will open the wrong one. It is not part of the
   pipeline and was left as-is — do not demo it, or point it explicitly at
   `synthetic_telemetry.csv` first.
7. The old real dataset `data/system_performance_metrics.csv` is unused dead
   weight kept for provenance.
8. Severity is predicted independently of incident type; a wrong type prediction
   still yields a severity.

## If a judge pushes hard, concede these

- **The simulation is not validated.** It's a transparent assumption model. Say
  so directly; don't defend it as predictive.
- **The dataset is synthetic and rule-based**, so strong classifier numbers are
  partly circular. The mitigations (held-out servers, borderline windows, class
  confusion that actually shows up) make it *less* circular, not non-circular.
- **`risk_score` is relative within one incident**, not an absolute safety
  measure, and not comparable between incidents.
- **Anomaly detector precision is 0.71.** It's a recall-oriented "screen", and
  the classifier is the component that actually names the problem.
- Real deployment would need: real labelled incident data, a validated outcome
  model (or A/B/historical data on past remediations), causal handling of
  overlapping incidents, and streaming/online inference instead of batch windows.
